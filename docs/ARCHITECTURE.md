# 통합 학습 시스템 설계

변호사시험 대비 학습 시스템 전체 구조. `CASE_Practice`(사례형)는 그중 하나의 위성 앱이다.
이 문서는 **네 개 앱이 공유하는 규약**을 정의한다 — 다른 앱을 만들거나 고칠 때 여기부터 읽을 것.

---

## 1. 허브 + 위성 구조

```
evenoa9218-gif.github.io/          ← 허브 (루트 저장소)
├── /                              대시보드·공용 서비스워커·PWA 매니페스트   [미구축]
├── /MCQ/                          선택형 (구 저장소명 3000)                [배포됨]
├── /CASE_Practice/                사례형 (구 저장소명 BarExam_Mastery)      [배포됨 = 이 저장소]
├── /Core_Notes/                   암기장 (구 저장소명 LawMJ-Mastery)        [배포됨, 다른 계정 작업]
└── /RECORD/                       기록형                                  [예정]
```

**허브 저장소 이름은 반드시 `evenoa9218-gif.github.io`여야 한다.**
GitHub Pages에서 이 이름만 사이트 루트(`/`)에 배포되고, 나머지는 `/저장소명/` 하위로 들어간다.
서비스워커 스코프와 PWA 설치 범위를 `/` 전체로 잡으려면 루트 저장소가 필요하다.

### 왜 한 오리진 안에 모으는가

네 앱이 **같은 오리진**(`evenoa9218-gif.github.io`)에 있어야 하는 이유:

- `localStorage` / `IndexedDB`가 오리진 단위로 격리된다 → 다른 오리진이면 학습 기록을 공유할 수 없다
- 서비스워커 스코프도 오리진 + 경로 기준이다 → 허브 하나로 네 앱을 오프라인 캐싱할 수 있다
- 앱 간 이동 시 재로그인이 없다

그래서 **다른 계정과 협업할 때도 저장소를 그 사람 계정으로 옮기지 않는다.**
계정·비밀번호를 공유하는 것도 아니고, **GitHub Collaborator로 초대**해서
오리진을 `evenoa9218-gif.github.io` 산하에 유지한다.

## 2. 저장 계층 — `core/store.js`

네 앱이 공유하는 저장 추상화. 이 저장소의 [`core/store.js`](../core/store.js)가 정본이다.

### 공개 API — 이 표면은 바꾸지 않는다

```js
Store.init({remoteUrl})          // IndexedDB 열기 + 원격 연결(선택)
Store.getUser() / setUser(uid)
Store.record(result)             // 학습 결과 1건 (선택형 채점 / 사례형 제출 공용)
Store.getRecords(filter) / deleteRecord(at)
Store.getMastery(subject)        // 쟁점 ID별 숙달도 집계
Store.getProgress(subject, round) / setProgress(...)
Store.getDraft(key) / setDraft(key, text) / clearDraft(key)
Store.sync(subject)              // 원격 → 로컬 병합
```

내부 구현(IndexedDB → 나중에 Firestore)이 바뀌어도 **호출부는 손대지 않는다**는 것이 설계 전제다.
API를 먼저 고정하고 구현을 갈아끼우는 방식.

### 왜 localStorage가 아닌 IndexedDB인가

사례형 답안은 한 건에 수천 자다. localStorage는 오리진당 약 5MB라 회독을 거듭하면 금방 찬다.
IndexedDB에는 용량 제한이 사실상 없다. 다만 `lawhub_uid`(현재 사용자)와
UI 설정(테마, 마지막 과목, 2단 분할 비율)처럼 작고 동기적으로 읽어야 하는 값은 localStorage에 둔다.

### 데이터 저장 위치와 프라이버시 경계

| 데이터 | 로컬(IndexedDB) | 원격(RTDB) |
|---|:-:|:-:|
| 답안 전문 (`text`) | ○ | **✕** |
| 채점 피드백 (`feedback`) | ○ | **✕** |
| 점수·소요시간·쟁점ID·회차 | ○ | ○ |
| 진도(회독별 완료 여부) | ○ | ○ |

**답안 전문과 피드백은 절대 원격으로 보내지 않는다.**
재사용 중인 Firebase RTDB가 인증 없는 공개 상태라, URL만 알면 누구나 읽을 수 있기 때문이다.
`Store.record()`가 원격 전송 직전에 `text`와 `feedback`을 구조분해로 떼어낸다.
원격에 올라가는 건 통계 집계에 필요한 요약뿐이다.

### Firebase 재사용 규약

새 프로젝트를 만들지 않고 `MCQ`가 이미 쓰는 공개 RTDB를 재사용하되, 네임스페이스를 분리한다.

```
users/…          ← MCQ (선택형)
case_users/…     ← CASE_Practice (사례형)
```

## 3. 쟁점 ID — 네 앱을 잇는 척추

선택형에서 틀린 쟁점을 사례형에서 찾아 풀고, 암기장에서 그 쟁점 카드를 복습하는 —
앱 간 연결의 기준이 되는 유일한 공용 키다.

### 형식

```
PUB-0001    공법        (헌법 / 행정법 / 공법일반)
CRI-0001    형사법      (형법 / 형사소송법 / 형사법일반)
CIV-0001    민사법      (민법 / 민사소송법 / 상법)
INT-0001    국제법       (예정)
ITL-0001    국제거래법    (예정)
```

### 세 가지 설계 결정

1. **목차 위치를 ID에 넣지 않는다.** 기본서가 개정되어 목차가 바뀌면 위치 기반 ID는 전부 무효가 된다. 계층 정보는 별도 `path` 필드에 두고, ID 자체는 불변 일련번호로 유지한다.
2. **표기 흔들림은 `aliases`로 흡수한다.** "포괄위임입법금지원칙"/"포괄위임금지원칙"/"포괄위임금지"는 한 쟁점이다. 새 별칭이 발견되면 ID를 새로 발급하지 말고 기존 항목의 `aliases`에 추가한다.
3. **ID는 재사용하지 않는다.** 쟁점이 사라져도 번호를 비워둔다 — 기존 학습 기록의 `issueIds`가 다른 쟁점을 가리키게 되면 안 된다.

### 배포 위치

- `data/issues_{과목}.json` — 전체 레지스트리 (허브·암기장이 그대로 가져다 쓸 수 있게 앱마다 배포)
- `data/{과목}/index.json`의 `byIssue` — 쟁점 → 출제 시험 역인덱스

## 4. 앱 데이터 규약

```
data/
├── issues_{과목}.json            쟁점 레지스트리 (전체)
└── {과목}/
    ├── index.json               목록 화면용 경량 인덱스 + byIssue 역인덱스
    ├── exams/{시험ID}.json       회차별 상세 (문제 전문·채점기준표·모범답안)
    └── casebook_toc.json         사례집 목차 브라우저용 (공법만)
```

- **`index.json`은 목록 화면에서 한 번만 받는다.** 문제 전문은 여기 넣지 않는다 — 넣으면 첫 로딩에 수 MB를 받게 된다.
- **`exams/*.json`은 문제를 열 때 그때 받는다.** 파일명은 시험 ID와 1:1이다.
- **시험 ID는 `{과목}_{변시|모의}_{회차}_사례`** 형식이고 변하지 않는다 — 학습 기록의 `examId`가 이걸 가리킨다.

생성 방법은 [`../pipeline/README.md`](../pipeline/README.md) 참고.

## 5. 문항 구조 — "제N문"

변호사시험 사례형 답안지는 **문항(제N문) 단위로 분리**된다. 앱의 페이지 분할도 이 단위를 따른다.

### 100점 규칙

공법 15회 실제 PDF로 확인한 규칙:

- 사례형 한 과목은 **문(제N문)당 정확히 100점**
- 한 문 안에 사실관계가 여럿이면 `제N문의1`, `제N문의2`…로 나뉜다
- 예 — 15회 공법: 제1문의1(35) + 제1문의2(35) + 제1문의3(30) = 100, 제2문 = 100

`relabel_groups.py`가 그룹 배점을 순서대로 누적하다 100점에서 문을 닫는 방식으로 라벨을 부여한다.
공법·형사법 110건 중 105건이 정확히 맞았다.

### 민사법은 100점 규칙이 성립하지 않는다 — 실제 PDF로 확인

제15회 민사법 실제 시험지를 대조한 결과 **문당 배점이 일정하지 않다.**

| 문항 | 배점 | 사례 수 |
|---|--:|--:|
| 제1문 | 150 | 6 (제1문의1~6) |
| 제2문 | 100 | 4 |
| 제3문 | 100 | 2 |
| **합계** | **350** | 12 |

100점 규칙을 적용했을 때는 제1문~제4문(100/105/115/30)으로 갈렸다 — 문항 수도 배점도 틀렸다.
민사법은 배점 누적으로 문 경계를 찾을 수 없다.

그래서 민사법만 [`relabel_civil.py`](../pipeline/scripts/relabel_civil.py)로 따로 처리한다.
라벨 근거를 아래 우선순위로 찾고, **근거가 없으면 라벨을 만들어내지 않는다.**

1. **원문 표제** — 문제 원문에 `[제1문의 1]`이 그대로 남아 있는 회차 (18건)
2. **채점기준표** — `[제N문의 M]` 섹션의 설문을 원문에서 찾아 위치를 확정 (매칭 실패 시 포기)
3. **실제 PDF 대조** — 제15회 변시 (1건, `MANUAL`에 직접 기입)

나머지 36건은 근거가 없어 기존 추정 라벨을 그대로 두되, `groupSource: "estimated"`로
표시해 목록에 `(추정)`, 풀이 화면에 안내 문구가 뜨게 했다. 틀린 라벨을 확정된 것처럼
보여주지 않는 것이 목적이다.

### 문항 분할을 텍스트 마커로 하지 않는 이유

`제N문` 같은 텍스트 마커로 나누는 방식을 시도했다가 버렸다 — 55건 중 마커가 있는 건 1건뿐이었다.
`【참조조문】` 같은 블록 경계로 나누는 것도 회차마다 포맷이 달라 불안정했다.
지금은 태깅 단계에서 이미 구조화된 **`questionStructure` 필드를 그룹핑**하는 방식을 쓴다.

## 6. 화면 규약

- **디자인 토큰은 `MCQ`의 라이트 테마를 따른다** (배경 `#ecf4fb` 등). 네 앱의 인상이 같아야 한다. 다크모드는 토글로 제공.
- **사례형 풀이 화면은 좌우 2단** — 왼쪽 문제, 오른쪽 답안. 실제 CBT 시험(eves) 화면을 따랐다. 위/아래로 쌓으면 답안을 쓰면서 지문을 보려고 계속 스크롤해야 한다. 두 단은 각각 독립 스크롤하고, 가운데 분할선을 끌어 폭을 조절할 수 있다(25~75%, localStorage에 유지).
- **860px 미만에서는 1단으로 접힌다.**
- **답안 임시저장은 문항 단위** — `Store.setDraft('{examId}::{groupKey}', text)`.

## 7. 빌드하지 않는다

`index.html` 한 파일에 React + Babel을 CDN으로 불러 쓴다. 번들러도 `node_modules`도 없다.

이유: GitHub Pages에 정적 파일로 그대로 올라가고, 파일 하나만 편집하면 배포가 끝나기 때문이다.
학습 앱 규모에서 빌드 파이프라인의 이득보다 "클론하면 바로 열린다"는 단순함이 크다.

대신 **런타임 Babel 변환 비용이 있으므로 앱이 커지면 재검토**해야 한다.

## 8. AI 자동채점 — 미구현

정적 페이지라 API 키를 클라이언트에 둘 수 없다(공개 저장소이므로 즉시 노출된다).

계획: **Cloudflare Worker 프록시**를 두고 키는 Worker 환경변수에만 보관.
앱은 Worker 엔드포인트로 답안과 채점기준표를 보내고 피드백만 받는다.
받은 피드백은 `Store.record({feedback})`로 **로컬에만** 저장한다(위 3절 프라이버시 경계).
